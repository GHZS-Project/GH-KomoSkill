# 上下文与留档（防失忆）

> 目标：**换一个会话，能靠文件把自己接回来**，而不是靠用户重新讲一遍。
> 手段不是「记住更多」，而是「把该记的写到对的地方，把不该记的压掉」。

---

## 一、留档三件套（各写各的，不许混）

| 文件 | 写什么 | **不写什么** | 位置 |
|---|---|---|---|
| `PROJECT.md` | 目标、当前阶段、关键约定、未决项、已知坑 | 日常流水 | `<项目>/.workbuddy/memory/PROJECT.md` |
| `YYYY-MM-DD.md` | 今天做了什么、踩了什么坑 | 需要长期维护的约定 | `<项目>/.workbuddy/memory/` |
| `PLAN.md` | 当前方案、影响面、验收标准 | 历史方案（归档进 `docs/`） | `<项目>/PLAN.md` |
| `CHANGELOG.md` | 版本级变更 + **为什么** | 逐次提交流水（那是 git 的事） | `<项目>/CHANGELOG.md` |
| `flow.json` | 阶段状态、门禁勾选、推进历史 | 业务内容 | `<项目>/.workbuddy/flow.json` |

### 单一事实来源原则

**长期约定只写在 `PROJECT.md`；日志只写「今天干了什么」。**

两处都写 = 迟早打架。打架之后谁对？没人知道 —— 这就是失忆的开始。

---

## 二、四级压缩

上下文会撑爆，所以要压。但**压错东西比不压更糟**。

| 级别 | 内容 | 放哪 | 对话里留什么 |
|---|---|---|---|
| **L0 原文** | 抓取原文、工具大输出、日志、报错堆栈 | `<项目>/outputs/raw/` 或 `.workbuddy/logs/` | **只留路径 + 行数** |
| **L1 摘要** | 决策、结论、关键数字、报错要点 | `.workbuddy/memory/YYYY-MM-DD.md` | ≤15 行阶段小结 |
| **L2 指针** | 「在哪、叫什么」 | `PROJECT.md` / `PLAN.md` | 一行索引 |

### 压缩红线（一条都不许压）

- **数字** —— 金额、条数、百分比、端口、版本号
- **路径** —— 绝对路径、文件名
- **命令** —— 可复现的那一行
- **报错原文** —— 可搜索的关键串
- **决策理由** —— 「为什么这么改」

> 只压**叙述与铺垫**，不压**可核查事实**。
> 检验标准：**压缩后若无法复现，就是压过头了。**

### L1 摘要模板（≤15 行）

```markdown
## 2026-10-26 · <项目名>
- 目标：<一句话>
- 做了：① … ② …
- 关键数字：<必须实测>
- 产物：<绝对路径>
- 坑：<下次会再遇到的>
- 下一步：<一条>
```

## 三、防失忆 5 条

1. **开场先跑简报** —— 任何续作、换任务、上下文跑偏，第一条命令是
   `python scripts/project_brief.py <项目目录>`（输出 ≤22 行，直接摆出
   目标 / 阶段 / 未决项 / 下一步 / 关键约定 / 已知坑 / 最近日志）。
2. **每阶段写日志** —— `YYYY-MM-DD.md` **追加，永不覆盖**。
3. **单一事实来源** —— 长期约定只写 `PROJECT.md`。
4. **记「为什么」不只记「改了什么」** —— 下次的自己最需要的是决策理由。
5. **交接块** —— 阶段结束时用固定五要素收口：
   `做了什么 / 产物路径 / 关键数字 / 下一步 / 风险`

---

## 四、跨会话恢复三步

新会话开始，按顺序：

```bash
python scripts/project_brief.py <项目目录>              # 1) 读简报，召回上下文
python scripts/flow_state.py <项目目录>                 # 2) 看阶段与门禁
python scripts/flow_state.py <项目目录> --gate <当前阶段>  # 3) 确认门禁是否已过
```

三步走完再动手。

> **跳过这三步直接改文件 = 高概率在错误的项目 / 错误的阶段里动手。**

---

## 五、项目隔离

- 每个项目**独立**维护上下文；新项目**不继承**历史对话。
- 续作时自动召回**对应项目**的上下文，不是「上一个项目」的。
- 同一会话里切项目时，明确说一句「现在切到 X 项目」再动手。

---

## 六、什么不该留

- 密钥、token、`.env` 内容（**任何情况下不写进日志**）
- 用户隐私数据原文（留路径即可）
- 一次性调试输出（用完删，或放 `outputs/raw/` 并注明可删）
- 已被推翻的旧方案（要么归档进 `docs/archive/`，要么删掉 —— 留在正文里会误导下次的自己）

---

## 七、一句话总结

> **留档不是为了「记录全部」，而是为了「下一个会话能用 22 行接上」。**
> 如果简报读完之后你还是不知道该干什么，说明 `PROJECT.md` 写错了对象 —— 它该写「约定与未决」，不是写流水账。
