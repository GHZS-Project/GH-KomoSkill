## S0 进场判断

**输入**：用户的一句原始需求（可能只有 4 个字）。

**动作**（三个判断，30 秒内完成，不占用用户确认）：

| 判断维度 | 取值 | 影响 |
|---|---|---|
| **类型** | 新建 / 续作 / 修补 / 调研 | 续作必须先跑简报召回上下文；修补必须读旧代码 |
| **风险** | 低（只读、生成新文件）/ 中（改代码、装依赖）/ 高（删数据、改系统、强推远端） | 高风险必须二次确认 + 备份 |
| **步数** | ≤3 步且可逆 / 否则 | ≤3 步可逆**可以**跳 S3，但必须先告知用户「我直接做了」 |

**输出**：无（心里有数）。

**门禁**：三维度判完才允许写文件。判不出来 = 需求太模糊，直接进 S1 问。

## S1 需求补全

**输入**：S0 的判断结果。

**动作**：校验 **4 要素**，缺哪项问哪项，**一次只问一个**。

| 要素 | 问法 | 判断标准（什么算齐了） |
|---|---|---|
| **场景用途** | 「这个工具解决什么问题？什么场景下用？」 | 能说清「谁在什么时候用它干什么」 |
| **交付产物** | 「最终要得到什么？脚本 / 网页 / 小工具 / 文档？」 | 有**具体形态**，不是「一个方案」 |
| **核心功能** | 「主要实现什么功能？最不能少的是哪一个？」 | 有**主功能**，能分清主次 |
| **约束偏好** | 「技术栈有偏好吗？放哪个目录？允许装依赖吗？」 | 有**边界**，或用户明确说「你定」 |

**同时产出六字段 Prompt**（见 `prompt-normalize.md`）—— 这是把口语翻成可判定需求的关键动作。

**输出**：需求确认单（见下方模板 A）。

**门禁**：用户回「确认 / 对 / 可以」。**不许自作主张往下走。**

---

## S2 项目启动确认

**输入**：需求确认单。

**动作**：补齐 **8 项**，匹配能力集。

| # | 项 | 说明 |
|---|---|---|
| 1 | 项目类型 | 工具 / 脚本 / 网页 / 小程序 / H5 / 自动化 / 数据处理 |
| 2 | 项目目标 | 一句话，与需求确认单一致 |
| 3 | 预计技术栈 | 尽量少；能用原生就不用框架 |
| 4 | 建议调用能力 | 候选技能/库/工具，**必须验证存在**（见 `capability-routing.md`） |
| 5 | 是否包含前端 | 涉及页面/UI/组件就要显式给建议，不能默认跳过 |
| 6 | 默认项目目录 | 绝对路径，落在用户授权范围内 |
| 7 | 主要交付内容 | 文件清单级别 |
| 8 | 预计验证方式 | 怎么证明它是对的（命令 / 页面 / 数字比对） |

**⛔ 本阶段红线**：**禁止创建文件、禁止装依赖、禁止改配置。** 只分析、只出清单。

**输出**：启动确认清单（模板 B）。

**门禁**：用户回「确认」。能力项若未通过存在性检查，必须先说明替代方案。

## S3 执行计划

**输入**：已确认的启动清单。

**动作**：拆 **≤5 大步**，每步标 **四属性**。

| 属性 | 要求 |
|---|---|
| 做什么 | 一句动词短语 |
| 动什么 | 具体文件路径 / 目录，不写「相关文件」 |
| 怎么验 | 可执行的检查（跑命令 / 看输出 / 比数字） |
| 风险 | 低/中/高 + 回滚方式 |

**规则**：

- 超过 5 步 → 说明粒度太细，合并；或项目太大，先做最小可用版（MVP）。
- 每步必须**可独立验证**，不能出现「步骤 3 做完才知道步骤 1 错了」。
- 计划落盘为 `PLAN.md`（模板 C）。

**输出**：执行计划表 + `PLAN.md`。

**门禁**：用户回「确认」。（例外：S0 判为 ≤3 步可逆且已告知，可跳过。）

---

## S4 分步执行与管控

**输入**：已确认的计划。

**动作**：逐步执行，每步遵守：

1. **先说这一步做什么**（一句话），再动手。
2. **做完给产物路径**（绝对路径），不只说「已完成」。
3. **出阶段小结**（≤15 行）：做了什么 / 关键数字 / 下一步。
4. **大输出落盘**：抓取原文、日志、报错堆栈写到文件，对话里**只留路径 + 行数**。
5. **异常给 3 个方案**：不要卡住、不要瞎试。列出 A/B/C 及各自代价，让用户选。

**门禁**：每步都有小结。没有小结 = 这步没做完。

---

## S5 验收与交付

**输入**：全部产物。

**动作**：

1. 出**交付验收单**（模板 D）：五项齐全。
2. 做**自我反证**：构造一个「如果我没做对，这个检查会失败」的验证。
   - 代码：跑一次真实命令，贴输出。
   - 网页：看一眼渲染结果 / 比一次截图。
   - 数据：比一次条数或 md5。
   - 部署：拉线上文件与本地比 md5（**不能只看 HTTP 200**）。
3. 逐项对照 S1 的验收标准，**有一条没过就如实说没过**。

**输出**：交付验收单。

**门禁**：用户回「通过 / 过 / 行」。

---

## S6 归档与收尾

**输入**：已验收的项目。

**动作**：

1. 问是否推远端（GitHub / 私有仓库）。**绝不默认自动推送。**
2. 写留档：`PROJECT.md`（档案卡）+ `YYYY-MM-DD.md`（当日日志）+ `CHANGELOG.md`（版本级）。
3. 出**五项汇报**（模板见 `evidence-discipline.md`），**每个字段实测**。

**门禁**：五项汇报已输出，且「是否推远端」有明确答复。

## 附：四张单子模板

### A. 需求确认单

```markdown
## 需求确认单
- 项目名：
- 场景用途：
- 交付产物：            （形态 + 落在哪个目录）
- 核心功能：            （主功能 1-3 条，标出最不能少的）
- 约束偏好：            （技术栈 / 依赖 / 目录 / 不能动的东西）
- 明确不做的：
- 待核验项：            （拿不准、必须查证的点，不许猜）
→ 以上是否正确？确认后进入启动确认。
```

```markdown
|---|---|---|

```

### C. 执行计划表

```markdown
## 执行计划（≤5 步）
| 步 | 做什么 | 动什么（路径） | 怎么验 | 风险/回滚 |
|---|---|---|---|---|
| 1 | | | | |

```

### D. 交付验收单

```markdown
## 交付验收单
| # | 项 | 内容 |
|---|---|---|
| 1 | 交付物清单 | 文件 + 绝对路径（逐个列） |
| 2 | 功能验证 | 怎么跑 / 怎么点，实测结果 |

| 5 | 后续建议 | 下一步可以做什么 |
→ 是否验收通过？
```

## 阶段跳过规则

| 可跳 | 条件 | 必须做的事 |
|---|---|---|
| S3 | S0 判为 ≤3 步且可逆 | 先告知「我直接做了」，并说明为什么可逆 |
| S2 的部分项 | 纯只读调研类 | 仍需说清目录与验证方式 |
| **S1 / S5 不可跳** | — | 需求不清就做 = 返工；不验收就交付 = 事故 |
